## 1. サービスの目的

NASDAQ100構成銘柄を対象に、割安な成長株を定期的にメールで通知し、登録した銘柄について
日次でシグナル（トレンド・モメンタム・出来高）を監視する。利用者は1〜少数人を想定。

## 2. 利用者とユースケース

| ユースケース | 利用者アクション | 実現方法 |
|---|---|---|
| 銘柄を監視リストに登録する | 招待トークン付きURLでティッカーを入力し送信 | register-stock Lambda |
| 銘柄を監視リストから削除する | 一覧の[削除]リンクを押す | register-stock Lambda |
| 判定期間モードを切り替える | SHORT/MID/LONGをプルダウンで選択 | register-stock Lambda → `app_settings` |
| レポートを今すぐ送る | 「選定レポートを送る」「監視レポートを送る」ボタン | register-stock → daily-batch非同期起動 |
| 仕組みを確認する | 「この仕組みについて」リンク | `_render_info`説明ページ |
| （無関係な第三者が操作できない） | 招待トークンを知らない限り操作不可 | `approved_tokens`テーブルでの認証 |

## 3. 機能要件

### 3.1 選定レポート（定期・全モード対象銘柄スキャン）
- 対象: NASDAQ100構成銘柄
- 選定条件: 利益成長率 >= `MIN_GROWTH`、かつ 0 < PEG <= `MAX_PEG`
- 並び順: PEG昇順（同値は時価総額降順）
- 上位`TOP_N`件をメール送信
- **送信頻度はモードに依存する**:
  - SHORT: 毎営業日
  - MID: 毎週月曜（`WEEKLY_REPORT_WEEKDAY`）
  - LONG: 月初1〜7日の中の月曜（月1回）

### 3.2 監視レポート（日次・登録銘柄のみ）
- 対象: 監視リストに登録された銘柄のみ
- 頻度: **全モード共通で毎日**（選定レポートの頻度とは独立）
- 監視リストが空ならレポート自体を送らない
- 各銘柄についてトレンド・モメンタム・出来高の3シグナルを判定してメールに記載

### 3.3 シグナル判定

| シグナル | 判定内容 | モード依存 |
|---|---|---|
| トレンド | 移動平均のゴールデンクロス／デッドクロス、および並び順(パーフェクトオーダー) | 短期/長期線の日数、並び順フィルタの有無がモードごとに異なる（`config.PERIOD_PRESETS`） |
| モメンタム(RSI) | 判定サイクル平均RSIが`rsi_oversold`以下で買い、`rsi_overbought`以上で売り | 判定サイクル（当日/前週/前月の実取引日平均）がモードごとに異なる |
| 出来高 | 判定サイクル平均出来高が基準値の`volume_multiplier`倍以上で急増表示 | 中期・長期では基準値を判定期間より前の`volume_lookback`日間で計算（判定期間自体は除く） |

- 「実際の取引日」の平均は暦週(`W-SUN`)・暦月(`M`)単位で休場日を自然に除外する

### 3.4 期間モード切替
- SHORT/MID/LONGの3種類。`app_settings`テーブルの`period_mode`キーに保存
- 未設定・読み取り失敗時は既定値(`DEFAULT_PERIOD_MODE = MID`)で動作する（読めないだけで
  サービス全体を止めない）

### 3.5 認証
- 招待トークン（`approved_tokens`テーブルに存在する文字列）を`?token=`で渡さない限り、
  一切の操作（閲覧含む）ができない

### 3.6 監視リスト上限
- `MAX_WATCHLIST_SIZE`（既定5件）を超える登録はできない

## 4. 非機能要件

| 項目 | 現状の要件・制約 |
|---|---|
| 実行時間 | Lambdaタイムアウト300秒以内に選定レポート生成が完了すること（NASDAQ100規模） |
| 信頼性 | 外部API(NASDAQ非公式API, yfinance)が一部銘柄で失敗しても、その銘柄をスキップして処理継続すること。選定レポートは取得成功率が`MIN_FETCH_SUCCESS_RATIO`(50%)を下回ったら送信せずエラー通知に切り替えること。NASDAQ100構成銘柄リストはキャッシュを持ち、Nasdaq API障害時にフォールバックできること |
| セキュリティ | 招待トークンを知らない第三者が銘柄登録・削除・モード変更を一切できないこと |
| データ整合性 | DynamoDBへの書き込みでfloat型エラーが発生しないこと(`_to_dynamodb_safe`) |
| 可用性 | Function URLが常時到達可能であること（IAM/リソースポリシーの権限不足で403にならないこと） |
