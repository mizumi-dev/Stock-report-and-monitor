# テスト計画（JSTQB Test Planning）

対象: `feature/mode-report-frequency`時点の実装（`docs/requirements.md`が基準）。

## 目的

新規実装（モード別シグナル判定サイクル・選定レポート送信頻度）を含む現状のサービス全体を、
公開・複数人利用に耐えるかという観点でアドホック検証する。自動テスト基盤(TODO#4)は
別タスクとし、今回は人間+エージェントによる一巡確認。

## スコープ

含む: `docs/requirements.md`記載の機能要件・非機能要件全項目。
含まない: 自動テストの実装、UIの見た目改善、TODO.md優先度中〜低の項目の実装。

## テストレベル・タイプ（今回採用する組み合わせ）

- テストレベル: System（実AWS環境への実invoke）を中心に、Component相当の確認は
  ローカルでの合成データ計算で代替（`signals.py`の純粋関数部分）
- テストタイプ: 機能テスト（全項目）、非機能テスト（性能・信頼性・セキュリティを重点、
  ユーザビリティは説明ページの整合性確認のみ）、変更部分のテスト（直近実装が既存機能を
  壊していないかの回帰確認）
- 構造テスト(ホワイトボックス)は対象外（プロジェクト規模的に費用対効果が低い）

## リスクベース優先順位

| 優先度 | リスク | 該当項目 |
|---|---|---|
| 高 | 黙って失敗し誰も気づかない | エラー通知、外部API全滅時の挙動 |
| 高 | 認証がバイパスされる | トークン検証 |
| 高 | 直近実装が既存機能を壊す | 回帰確認（監視リスト、シグナル計算） |
| 中 | 性能・タイムアウト | 実行時間 |
| 低 | 表示のズレ | 説明ページの文言 |

## エントリー基準（テスト開始条件）

- `docs/requirements.md`が存在し、対象機能の合否基準が明文化されている（済み）
- `claudedeploy` AWSプロファイルで対象Lambda群にアクセスできる（確認済み: `sts get-caller-identity`成功）

## 終了基準（Exit Criteria）

- `docs/test-cases.md`の全ケースを実行し、結果を記録した
- 優先度「高」のケースに未解決の不合格がない
- 見つかった欠陥は全て`TODO.md`に反映した

## 実施体制

1人開発（ユーザー）+ エージェント。エージェントが計画・設計・実行・記録を行い、
ユーザーは方針確認と最終承認を行う。

今回のセッション内で一巡実施。継続的な実施は将来的にCI化を検討（TODO#4/#12）。
